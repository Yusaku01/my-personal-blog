古いシステムを新しいシステムへ置き換える方法の1つに、すべてを作り直して一度に切り替える方法があります。

個人の小規模なプロジェクトや、まだ利用者がいないシステムでは有効な場合もあります。
しかし、規模が大きく、現在も利用されているシステムは簡単には止められません。
一度に切り替える変更範囲が広いほど、失敗したときの影響も大きくなります。

このような一括置換を避け、既存システムを動かしながら段階的に移行する考え方が、**Strangler Fig Application**（ストラングラー・フィグ・アプリケーション）です。

Strangler Fig Applicationが扱うのは、移行後のシステム構成そのものではなく、**稼働中のシステムが担う責務を、どのように新しいシステムへ移していくか**です。

## Strangler Fig Applicationとは

Strangler Fig Applicationは、稼働中の既存システムが担う機能や振る舞いを小さな単位で新しいシステムへ移し、旧システムの役割を徐々に減らしていく、レガシーモダナイゼーションの漸進的な移行アプローチです。

文脈によって、アーキテクチャパターン、移行パターン、デザインパターンなどと呼ばれます。

ただし、StrategyやObserverのようにクラスやオブジェクトの構造を決める、いわゆるGoFのデザインパターンとは扱う範囲が異なります。
Strangler Fig Applicationは、システム全体をどのような手順で移行するかを扱う知見です。

この名称と比喩をソフトウェア移行の文脈へ導入したのは、Martin Fowler（マーティン・ファウラー）氏です。
Fowlerは2004年に「Strangler Application」を公開し、2019年に「Strangler Fig Application」へ改題しました。
さらに2024年には、この考え方をレガシーモダナイゼーションの文脈から整理した「Strangler Fig」を公開しています。

名前の由来は、Fowlerがオーストラリアのクイーンズランドで見たStrangler Figというイチジクです。
この植物は別の木を支えにして成長し、根を地面まで伸ばしながら宿主を覆います。
やがて自立し、場合によっては宿主の木が枯れたあとも、その場所に残ります。

Fowlerはこの成長過程を、既存システムの周囲で新しいシステムを育て、振る舞いを少しずつ移していく方法に重ねました。

## 技術的な移行を始める前に決めること

Strangler Fig Applicationは、単に古いコードを新しいコードへ置き換える手法ではありません。

Fowlerが2024年に整理した説明では、漸進的なモダナイゼーションに必要な活動として、次の4つが挙げられています。

1. 達成したい成果を理解する
2. 問題を小さな部分へ分ける
3. 分けた部分を実際に提供する
4. 継続できるように組織を変える

たとえば、移行の目的は次のように異なります。

- 変更にかかる時間や費用を減らす
- サポートが終了した技術を廃止する
- 新しい機能を短期間で提供できるようにする
- 複雑になった業務プロセスを改善する
- 特定のシステムやベンダーへの依存を減らす

目的が曖昧なままでは、新しい技術へ移しても、事業や運用上の問題が解決されない可能性があります。
そのため、移行先の技術を選ぶ前に、何を改善できたら移行が成功なのかを明確にします。

## 「何を移すか」と「どこで切り替えるか」

Strangler Fig Applicationでは、次の2つを分けて考えます。

### 移行単位

移行単位とは、既存システムから新しいシステムへ移す責務のまとまりです。

たとえば、次のような単位があります。

- 機能
- ビジネス能力
- ドメイン
- 商品やサービスの種類
- URLや画面
- データの一部分

### Seam

**Seam**とは、既存システムと新しいシステムを分離し、呼び出し先を分岐または差し替えられる接点です。

たとえば、次の場所にSeamを作れます。

- URLルーティング
- APIの境界
- イベント
- 抽象化レイヤー
- データアクセス層
- Repository

つまり、機能やドメインは「何を移すか」であり、URLルーターやAPI、イベントは「どこで切り替えるか」です。
両者は関連していますが、同じものではありません。

## FacadeやProxyを使った移行

WebサイトやWebアプリケーションでは、利用者から届くリクエストを既存システムと新しいシステムへ振り分ける、FacadeやProxyを置く方法がよく使われます。

```text
利用者
  ↓
Facade / Proxy
  ├─ 未移行の責務 → 既存システム
  └─ 移行済みの責務 → 新しいシステム
```

Facadeはリクエストの内容を確認し、未移行の機能を既存システムへ、移行済みの機能を新しいシステムへ振り分けます。

移行は、たとえば次の流れで進みます。

1. 移行によって達成したい成果を決める
2. 小さく移行できる責務と、そのためのSeamを見つける
3. 新しいシステムへ対象の機能を実装する
4. 呼び出し先を新しいシステムへ切り替える
5. 動作を検証し、必要であれば既存システムへ戻す
6. 同じ手順を繰り返し、既存システムの役割を減らす
7. 不要になった旧機能と移行用の仕組みを削除する

たとえばWebサイトをURL単位で移行する場合は、最初に1つのページだけを新しいシステムへ移します。
問題がなければ対象URLを増やし、既存システムが担当する範囲を徐々に減らします。

ただし、FacadeやProxyは代表的な実装方法であり、Strangler Fig Applicationの必須構成ではありません。
システムの構造に応じて、APIの抽象層、イベントルーター、Repository、データアクセス境界などもSeamとして利用できます。

## Transitional Architecture

移行中だけ必要になるルーティング、互換層、データ同期処理などの構造は、**Transitional Architecture**と呼ばれます。

Transitional Architectureは、移行後の最終的なシステムには必要ない場合があります。
それでも、新旧のシステムを同時に動かしながら安全に責務を移すには、一時的な仕組みへの投資が必要です。

建物の改修における足場のようなもので、完成後には撤去しますが、工事中の安全性を確保するためには欠かせません。

Transitional Architectureを導入するときは、少なくとも次の内容を決めます。

- なぜ必要なのか
- 誰が管理するのか
- どの状態になれば削除できるのか
- 移行完了をどのように判定するのか

仮設の足場が、いつの間にか本館にならないようにする必要があります。

## 移行先の構造を決めるパターンではない

Strangler Fig Applicationは、移行後のシステムをマイクロサービスにするためだけの方法ではありません。

モノリスからマイクロサービスへの移行例でよく紹介されます。
しかし、段階的に移せる責務とSeamを見つけられるなら、ほかの移行にも適用できます。

- 古いフレームワークから新しいフレームワークへの移行
- 旧CMSから新CMSへの移行
- モノリスからモジュラーモノリスへの移行
- 自社システムからSaaSへの移行
- 古いデータベースから新しいデータベースへの移行
- 特定の機能だけを外部サービスへ置き換える移行

「どのようなシステム構成にするか」と「稼働中のシステムをどう移行するか」は、別々に考える必要があります。

| 知見の種類 | 答える問い | 例 |
| --- | --- | --- |
| アーキテクチャスタイル | 最終的にどのような構造にするか | モノリス、モジュラーモノリス、マイクロサービス |
| 移行アプローチ | 稼働中のシステムから責務をどう移すか | Strangler Fig Application |
| デプロイ戦略 | 新旧の実行環境をどう配置し、トラフィックを切り替えるか | Blue-Green Deployment |
| リリース戦略 | 新しいバージョンを誰に、どの範囲から公開するか | Canary Release |

Blue-Green Deploymentでは、できるだけ同じ構成の2つの本番環境を用意し、ルーターなどを使って稼働環境を切り替えます。

Canary Releaseでは、最初に一部の利用者、地域、ブランド、トラフィックなどへ新しいバージョンを公開します。
問題がないことを確認しながら、公開対象を広げます。

一方、Strangler Fig Applicationが扱うのは、既存システムが担うどの責務を、どの順番で新しいシステムへ移すかです。

## 利点と難しさ

段階的な移行では、1回あたりの変更範囲を小さく保てます。
機能ごとに動作を確認できるため、問題が起きた場合の影響や切り戻し範囲も限定しやすくなります。

また、システム全体の完成を待たずに、移行できた部分から利用者や事業へ価値を提供できます。
実際の移行で得た学びを、次の移行判断へ反映できる点も利点です。

一方で、移行期間中は新旧2つのシステムを保守する必要があります。

特に、次の問題を事前に考えなければなりません。

- どちらのシステムがデータの正しい持ち主なのか
- 新旧で共有するデータをどう同期するのか
- 新旧システム間の呼び出しをどう管理するのか
- どの時点まで旧システムへ戻せるのか
- 移行用の仕組みをいつ削除するのか

FacadeやProxyがすべてのリクエストを受ける場合は、単一障害点や性能上のボトルネックになる可能性もあります。

また、次のような場合には、Strangler Fig Applicationが適さないことがあります。

- リクエストや処理を途中で分岐できない
- システムが小さく、一括で置き換えてもリスクが小さい
- 旧システムを短期間で完全に停止する必要がある
- 新旧システムを長期間共存させられない

段階的であること自体が目的ではありません。
一括置換よりも段階的な移行の方が、リスクや費用を抑えられる場合に選択します。

## 一緒に使われる関連パターン

Strangler Fig Applicationは移行全体の進め方を扱います。
移行中に発生する個別の問題は、別のパターンや手法を組み合わせて扱います。

- **Branch by Abstraction**：抽象層の裏側で、古い実装を新しい実装へ段階的に差し替える
- **Event Interception**：既存のイベントを捕捉し、新しいシステムへ転送または複製する
- **Parallel Change**：APIやデータ構造を一時的に新旧両方へ対応させ、利用側を移したあとに古い契約を削除する
- **Anti-Corruption Layer**：古いシステムのデータや用語を変換し、レガシー側の設計を新しいシステムへ持ち込まないようにする
- **Repository**：データへの直接アクセスを抽象化し、データの取得先を切り替えられる境界を作る
- **Feature ToggleやCanary Release**：新しい実装を利用する環境や利用者を制限し、公開範囲を段階的に広げる

これらはStrangler Fig Applicationそのものではありません。

たとえばCanary Releaseが扱うのは、新しいバージョンをどの利用者や地域から公開するかです。
Strangler Fig Applicationが扱うのは、どの機能や責務を既存システムから新しいシステムへ移すかです。

また、URLごとの担当を記録する台帳やルーティング設定も、それだけでStrangler Fig Applicationになるわけではありません。
これらは、段階的な移行を実現するTransitional Architectureの一部です。

## 移行を考えるための7つの問い

Strangler Fig Applicationを実際のシステムへ当てはめるときは、次の問いから考えられます。

1. この移行によって、どのような成果を得たいか
2. 何を単位として移行するか
3. どこにSeamを作るか
4. 新旧システムのデータと責務をどう管理するか
5. どう検証し、問題が起きたらどう切り戻すか
6. 誰が移行を所有し、継続的に進めるか
7. 何を削除できたら移行完了とするか

Strangler Fig Applicationは、単に古いシステムと新しいシステムを共存させる方法ではありません。
達成したい成果を明確にし、小さく移せる責務とSeamを見つけ、価値を提供しながら新しい側へ責務を移すアプローチです。

最終的には、役割を失った旧機能と不要になったTransitional Architectureを撤去することを目標とします。
Facadeなどが移行後も互換アダプターとして必要なら、目的と所有者を明確にしたうえで残す場合もあります。
